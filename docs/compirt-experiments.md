  # CompIRT Experiments

This implementation follows the paper's two-stage model structure using the
local HuggingFace tables and direct Pyro models. The current tossup stage uses
SVI rather than the paper's proposed NumPyro NUTS-MCMC inference.

## Implemented Equations

- Equation 3: logistic position-dependent tossup difficulty
- Equation 4: conditional buzz correctness
- Equations 5--7: discrete buzz hazard, survival, and first-buzzer competing risks
- Equation 13: dead-tossup survival
- Equation 8: the paper's literal unnormalized log-sum-exp aggregation
- Equations 10--11: optional pairwise synergy and bonus-part outcome model

Per-game lineups are inferred from buzz evidence (`lineup.py`, cached under
`data/lineups/`) rather than the full registered roster; games with no buzz
evidence fall back to the full roster. The tossup likelihood uses the first
recorded buzz only. Later bounce-back after a
neg is deferred because the paper leaves its full derivation unfinished. Packet
positions that cannot be matched to a known tossup are skipped. Bonus training
keeps fitted tossup skills fixed.

The source PDF is a draft specification and is not generated by this
repository.

## Setup And Data

The scripts require `torch`, `pyro-ppl`, `datasets`, `pandas`, `matplotlib`, and
`scikit-learn`.

Create the project-local environment:

```bash
python -m venv --system-site-packages .venv
.venv/bin/pip install -r requirements/dev.txt
```

`requirements/compirt.txt` contains runtime dependencies only. The development
requirements add the static checker used by the repository verification command.

Rebuild the local HuggingFace data after adding `games.packet_id`:

```bash
.venv/bin/python -m data_pipeline.build --overwrite
.venv/bin/python -m data_pipeline.validate
```

Inspect the real-data observation tables:

```bash
.venv/bin/python compirt_data.py --tournament 2024-acf-regionals-cornell
```

## Pyramidal IRT

Fit the competing-risks model with dead tossups:

```bash
.venv/bin/python train_pyramidal.py \
  --tournament 2024-acf-regionals-cornell \
  --steps 1000 \
  --output-dir results/compirt/cornell/pyramidal
```

Every pyramidal run also writes expected first-buzz positions to
`buzz_event_predictions.csv`.

## Compositional IRT

Fit the default no-synergy bonus model:

```bash
.venv/bin/python train_compositional.py \
  --tournament 2024-acf-regionals-cornell \
  --player-skills results/compirt/cornell/pyramidal/players.csv \
  --steps 1000 \
  --output-dir results/compirt/cornell/compositional
```

Enable the paper's synergy term:

```bash
.venv/bin/python train_compositional.py \
  --tournament 2024-acf-regionals-cornell \
  --player-skills results/compirt/cornell/pyramidal/players.csv \
  --use-synergy \
  --synergy-dimensions 1 \
  --save-synergy-details \
  --steps 1000 \
  --output-dir results/compirt/cornell/synergy
```

`--save-synergy-details` is optional. It exports profiles and observed teammate
pairs, but is not needed for predictions.

The saved team synergy contribution is an unnormalized sum of every pairwise
profile dot product over the inferred game lineup. It is not a direct measure
of teamwork quality. Because lineups are inferred from buzz evidence rather than
observed, the contribution can still include players who did not actually play.
It also grows with the number of roster pairs and, when lineups are mostly
fixed, can act as a team-level intercept that compensates for the skill
aggregate or item
difficulties. Future synergy outputs include roster size, pair count,
per-pair contribution, and sign-rate diagnostics to make this confounding
visible. Interpret synergy only after held-out recombined-roster evaluation.

## Evaluation

```bash
.venv/bin/python evaluate_compirt.py \
  --pyramidal-results results/compirt/cornell/pyramidal \
  --compositional-results results/compirt/cornell/compositional \
  --output-dir results/compirt/cornell/evaluation
```

The evaluator runs the seeded match-winner diagnostic when the generated local
dataset is available. Add `--skip-game-simulation` when evaluating copied result
artifacts without `data/hf/`.

Training directories contain parameter CSV files, prediction CSV files, loss
plots, and `summary.json`. The evaluator owns the remaining diagnostic plots.
It reconstructs fitted first-buzz distributions from saved posterior medians,
so timing-fit diagnostics do not require retraining.

The main evaluation figures are aggregate tossup and bonus reliability with
ECE, tossup reliability stratified by buzz position, predicted versus
empirical first-buzz timing, tossup difficulty over empirical buzz locations,
and observed versus predicted buzz position and bonus points.

The evaluator also writes density dashboards for fitted player, tossup,
bonus-part, and optional synergy parameters. Vector parameters include both
coordinate distributions and rotation-invariant magnitude distributions.
`pyramidal_difficulty_curve_distribution.png` shows the median learned
difficulty curve with 25th--75th and 5th--95th percentile bands. The companion
parameter-distribution CSV files contain exact quantiles. A single fitted
scalar such as `tau` is omitted because it does not define a distribution.

### Final-round-fraction holdout

To train on the early rounds of every tournament and evaluate on the final 20
percent of rounds, run:

```bash
DEVICE=cuda ./run_scripts/common/run_compirt_round_holdout.sh
```

The wrapper defaults to `BASE_SPLIT=all` and
`ROUND_HOLDOUT_FRACTION=0.2`. For example, restrict the source data to 2024
with:

```bash
BASE_SPLIT=year_2024 ROUND_HOLDOUT_FRACTION=0.2 DEVICE=cuda \
  ./run_scripts/common/run_compirt_round_holdout.sh
```

For each tournament, the split holds out
`ceil(number_of_numbered_rounds * fraction)` complete rounds, with at least one
held-out round. Games in an unparseable round such as `roundNone` are assigned
to test so their unknown schedule position cannot leak into training. Related
tossup-buzz and bonus-response rows follow their game, so outcome tables are
disjoint even though question metadata may be shared.

This wrapper uses the repository's existing **transductive** holdout workflow:
training-player posteriors become priors, then test-player and test-item
parameters are co-estimated from the held-out outcomes being scored. It measures
late-round psychometric estimation, not a frozen pre-game forecast. The active
lineups are also inferred from each game's buzz evidence under the repository's
standard data convention.

When `RUN_SYNERGY=1`, `run_scripts/common/run_compirt.sh` writes separate reports for the two
bonus-model variants:

- `ROOT/evaluation/experiment_report.md`: no-synergy compositional model;
- `ROOT/synergy-evaluation/experiment_report.md`: synergy model.
- `ROOT/comparison/bonus_model_comparison.md`: direct metric comparison.
- `ROOT/comparison/bonus_model_comparison.png`: visual overall metric comparison.

The evaluator reports PPB MAE after averaging observed and predicted bonus
points within each game/team, matching the paper's game-level definition. The
discrete per-bonus comparison is `exact_acc` (do the predicted-correct parts
match the actual ones); a per-bonus expected-points MAE is intentionally not
reported.

## Dimension Ablations

Three runners sweep the latent dimensionality and plot held-out metrics against
it. Each fits the held-out pipeline per sweep point: Stage-1 train on
`TRAIN_SPLIT`, a Stage-1 held-out pass on `TEST_SPLIT`, Stage 2, then evaluation.
The `multidim` and `learned` runners fit a **synergy-only** Stage 2, so neither
writes a `holdout/compositional` branch.

```bash
# multidim MIRT: sweeps the latent skill dimension m
.venv/bin/python -m run_scripts.multidimensional.multidim.run_multidim_ablation --dimensions 1 2 3 4 5

# learned topic (joint sLDA): sweeps the topic count K, which *is* the skill dimension
.venv/bin/python -m run_scripts.topic.run_learned_topic_ablation --dimensions 1 2 3 4 5

# baseline: a 2-D grid over skill dimension m and synergy rank s
.venv/bin/python -m run_scripts.baseline.run_baseline_ablation \
    --dimensions 1 2 3 4 5 --synergy-dimensions 0 1 2 3
```

Each sweep point lands in `<root>/dim_<n>/{train,holdout}/...`, and the ablation
root collects them:

- `<root>/csvs/{baseline,multidim,learned_topic}_ablation_metrics.csv`: one row
  per point.
- `<root>/graphs/*_vs_dimensions.png` (baseline, multidim) or `*_vs_topics.png`
  (learned). The baseline runner also writes `*_grid.png` heatmaps.
- `<root>/ablation_config.json`: every resolved runner setting, written before
  training starts. A `--collect-only` pass never overwrites it.

Stages are resumable: each is skipped when its marker file (`summary.json`, or
`experiment_report.md` for evaluation) already exists. Pass `--rerun` to force
them. `--collect-only` rebuilds the aggregate CSV and graphs from existing run
folders without retraining, and `--plot-dimensions` aggregates a wider set than
the `--dimensions` you just trained — so a sweep can be extended incrementally.

The **baseline** runner sweeps two axes at once. `--dimensions` (`m`) is the
width of `theta_i` and of the free learned `alpha_j`; `m = 1` is the paper's
scalar-skill CompIRT and so is the reference row. `--synergy-dimensions` (`s`) is
the rank of the pairwise synergy term, and `s = 0` runs the no-synergy
compositional branch as the reference column. A point lands in
`<root>/dim_<m>/holdout/syn_<s>/`, whose bonus stage is named after the branch it
ran (`compositional/` at `s = 0`, `synergy/` otherwise). Two consequences of
Stage 1 not depending on `s`: the pyramidal fits are shared down each dimension's
whole synergy column, so an `|m| x |s|` grid costs only `|m|` Stage-1 fits; and
the tossup metrics are constant in `s`, so they are written into every CSV row
but plotted only against `m`. Only the bonus metrics get the 2-D heatmaps.

Baseline, multidimensional, and learned-topic sweeps are seeded (`--seed`,
default 42), thread that seed into their training stages, and record it in run
metadata. Small gaps between adjacent ablation points should still be read
cautiously because a single seed does not measure optimization variability.

The learned runner additionally exposes `--bow-weight`, `--topic-concentration`,
`--vocab-size`, `--min-df`, `--rm-top`, and `--seed`; every value it used is
recorded in `ablation_config.json`, in the per-point `summary.json`, and as
columns of the aggregate CSV. **Read the `K` curve with `--bow-weight` in mind.**
At its default of `1.0` the LDA word likelihood dominates the outcome likelihood
(~50--150 word tokens per document against a handful of buzzes), so topics come
out nearly unsupervised and a flat metric-vs-`K` curve is a plausible artifact
rather than evidence that topic count does not matter. When diagnosing this
tradeoff, sweep `--bow-weight` over roughly `0.05--1.0` against a held-out IRT
metric rather than interpreting the default alone.

## Drop Robustness (Ranking Sensitivity)

How stable is the player ranking when a small fraction of buzz events is
deleted? Following the data-dropping methodology of arXiv 2508.11847 (which
flipped Chatbot Arena's top model by removing 0.003% of its preferences), two
runners compare four ranking methods on identical dropped-event sets: raw
actual PPG (no model, no refit), plain IRT
(`simple_mirt/train_plain_irt.py`, the classical `sigmoid(alpha·theta − d)`
model), baseline CompIRT, and multidim CompIRT. The hypothesis under test is
that the CompIRT rankings degrade more gracefully than the simpler methods.
The full mathematical contract (functionals, agreement metrics, AMIP
relation) is `compirt_eval/drop_robustness/README.md`; this section covers commands
and interpretation. A completed Tier-1 run and its reading — including each
family's measured noise floor and the top-25 fragility asymmetry — is
`results/compirt/in_sample/common/drop-robustness/README.md`.

```bash
# Tier 1: random-drop robustness curves (average case)
./run_scripts/common/run_drop_robustness.sh
# equivalently
.venv/bin/python run_scripts/common/run_drop_robustness.py \
    --fractions 0.001 0.005 0.01 0.05 --replicates 3

# Tier 2: targeted worst-case drops (minimal refit-confirmed flip counts),
# reusing Tier 1's full and noise-floor fits
.venv/bin/python run_scripts/common/run_targeted_drop.py \
    --reuse-full results/compirt/in_sample/common/drop-robustness
```

Every fit is Stage-1 only (player ranking never touches Stage 2), in-sample on
`--split year_2024`, and uses **one fixed model seed** so full-vs-dropped
differences isolate the data effect. A drop list is a plain text file of
`event_id`s under `<root>/droplists/`; all three trainers accept it via
`--drop-events`, and the same list is applied to every method. Rankings are
rotation-invariant predicted-PPG scalars (see
`compirt_eval/common/player_scoring.py`), never raw `theta_k` coordinates.

Tier 1 writes `<root>/csvs/drop_robustness_metrics.csv` (one row per model x
fraction x replicate: Kendall tau, Spearman, top-5/10/25 Jaccard, top-25
displacement vs that model's own full-data ranking) and two curve plots under
`<root>/graphs/`. Tier 2 ranks a target player's events most-influential-first
(earliest correct buzzes for `--direction demote`), refits at increasing
prefix sizes, and reports each method's flip bracket in
`csvs/targeted_flip_metrics.csv` / `csvs/actual_flip_curve.csv` plus
`graphs/gap_vs_dropped.png`.

**Read every effect against the same model's own noise floor.** Each family
gets alternate-seed full-data fits (`--noise-seeds`, recorded as fraction-0
rows and shaded bands): SVI seed jitter alone moves these rankings (see
`results/compirt/in_sample/multidim/multidim-tanh-all2024-noisefloor/README.md` — note
that committed floor is for the tanh link, while this study defaults to
sigmoid, so the runners fit their own floors), and a drop-induced change
smaller than a family's own seed jitter is not a finding. Raw actual PPG is
deterministic, so its curve is pure data effect. The targeted selector is a
heuristic influence proxy, not the paper's exact AMIP: flips it finds are
refit-confirmed and therefore definitive, but a "no flip" result is not proof
that no flipping subset exists.

## Other Info

Healthy full-run outputs should have finite, generally decreasing loss curves;
difficulty curves that decline from early to late clues; plausible player
rankings; and reliability plots that approach the diagonal. The paper contains
no completed numeric target values for Buzz MAE, AUC, ECE, or PPB MAE. Synergy
scores should not be interpreted as useful unless a later held-out
recombined-team experiment shows improvement over the no-synergy model.

Cold-start learning curves and MCMC trace/R-hat plots still require repeated
adaptation fits or posterior samples. C1--C4 compositional generalization is
available through the opt-in temporal runner described below. The
timing-fit plot uses posterior medians and is therefore a fitted predictive
check rather than a full posterior-predictive check.

## Opt-in Scenario C

The temporal holdout runner can additionally test whether historical player
synergy profiles transfer to familiar, recombined, partially new, and fully new
test rosters. See
[`compirt_eval/SCENARIO_C.md`](../compirt_eval/SCENARIO_C.md) for the complete
implementation protocol, classification rules, and output schema.

```bash
RUN_C1_C4=1 MODEL=baseline DEVICE=cuda \
  .venv/bin/python -m run_scripts.common.run_compirt_holdout
```

Scenario C is disabled by default and does not change the existing Scenario A/B
outputs. It trains historical no-synergy and synergy bonus stages, freezes their
team-level parameters, and fits only the new test bonus-item parameters. Results
are written beneath `<resolved-root>/holdout/c1-c4/`.

Optional controls are `C1_C4_ITEM_STEPS` (defaults to `BONUS_STEPS`),
`C1_C4_MIN_CROSS_TEAM_GAMES` (default 10), and `C1_C4_SEED` (default 42).
Scenario C reports point estimates and sample sizes; it does not run bootstrap
resampling. The implementation supports the root bonus-stage families:
`baseline`, `multidim`, `tfidf`, and `tfidf_multidim`.

Equation 8 is implemented exactly as printed in the paper:
`tau * log(sum(exp(member_score / tau)))`. It is not normalized by roster size.
As a result, larger rosters receive a larger aggregate contribution,
and the aggregation does not approach the mean as `tau` grows despite the
paper's accompanying verbal claim.

Equation 13 is also implemented literally as `S(T_j)`. Because Equation 6
defines `S(t)` over positions strictly before `t`, the final token is not
included in that survival term.
